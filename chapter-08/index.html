Part 1 · The Idea, At Scale

Training = the Chapter-5 loop, 100,000 times

Nothing new happens in training — it's the exact loop from Chapter 5, now run over your recorded dataset:

  1. Grab a batch of recorded frames (camera + joints).
  2. ACT predicts the action chunk for each.
  3. Compare to what you actually did → the L1 loss (Chapters 4 & 5).
  4. Backprop → nudge every weight a little.
  5. Repeat ~100,000 times.
loss = | ACT's predicted motion − your recorded motion | averaged over the batch — exactly the regression loss from Chapter 5

Each pass makes ACT copy you a tiny bit better. Do it enough times and the network can generalize the pattern to new situations it never saw.

Part 2 · Vocabulary

Steps, batches & epochs

Batch

A handful of frames processed together before one weight update. LeRobot's default is batch_size = 8.

Step

One batch → one nudge of the weights. ACT trains for steps = 100,000 by default.

Epoch

One full pass over your whole dataset. Big datasets = many steps per epoch; small ones repeat often.

How much training is that?

Dataset size (frames)36,000

—passes over the data (epochs)

Assumes batch size 8. The same frames get revisited many times — that repetition is how the pattern sinks in.

The network sees each frame many times over a training run — like reviewing the same flashcards until the pattern is second nature. Too few steps and it hasn't learned; the graph on the next slide tells you when to stop. 📉

On a good GPU, 100k steps for ACT takes a few hours. On a laptop CPU it could take days — which is exactly why we'll borrow a cloud GPU soon. ☁️

Part 4 · Save Points

Checkpoints

Training for hours is risky — what if it crashes at step 90,000? So LeRobot saves the model to disk every save_freq = 20,000 steps (and at the end), into output_dir/checkpoints/.

Checkpoints are like save points in a video game:

  • Resume a crashed run with --resume=true instead of starting over.
  • Pick the best one — a later checkpoint isn't always better (see: overfitting).
  • Deploy any checkpoint by pointing --policy.path at it.
Click a save point → load different checkpoints and see how far along that version of the brain is.

☁️ Sub-section: Training in the cloud (Colab & Hugging Face)

Here's the beautiful part: your Mac never needs a GPU. The Hugging Face Hub is the bridge — you push the dataset up, a cloud GPU trains on it, and you pull the finished policy back down to run on the arm.

Google Colab gives you a free GPU in a browser notebook — great for a first training run. The flow:

  1. Record locally and let it upload: --dataset.push_to_hub=true (Chapter 7).
  2. Open LeRobot's ACT training notebook in Colab, switch the runtime to a GPU, and sign in with hf auth login.
  3. Run lerobot-train there — it pulls your dataset from the Hub and pushes the trained policy back.
# inside the Colab GPU notebook lerobot-train --dataset.repo_id=$HF_USER/grab_cube --policy.type=act \ --output_dir=outputs/train/act_grab_cube --policy.device=cuda \ --policy.repo_id=$HF_USER/act_grab_cube --wandb.enable=true

Hugging Face Jobs runs training on a managed GPU with one extra flag — no notebook, no setup. Add --job.target=<gpu> to the same command and it dispatches to the cloud.

# run hf auth login first; list GPUs with: hf jobs hardware lerobot-train --dataset.repo_id=$HF_USER/grab_cube --policy.type=act \ --policy.repo_id=$HF_USER/act_grab_cube \ --job.target=h200 --job.timeout=8h

The pod trains on the Hub dataset and pushes the policy to your account. --job.detach submits and exits; hf jobs hardware shows the flavors & pricing. Parts 6–8 below walk through this end to end: push your recorded episodes, launch the job, and watch the loss live.

Why the Hub matters: it decouples where you record (your Mac + arm) from where you train (a big GPU). Record here, train anywhere, run here. That's the whole cloud workflow. 🌉
Part 6 · Ship The Data

Push your recorded episodes to the Hugging Face Hub

A cloud GPU cannot see your Mac's disk. Before anything can train, the folder that lerobot-record wrote (Chapter 7, Part 9) has to live on the Hub under your username, as a dataset repo.

Step 0 · Sign in once

hf auth login # paste a token from huggingface.co/settings/tokens (write access) hf auth whoami # prints your username, e.g. anjaniksharma

Everything below uses that username as the namespace in front of the slash: anjaniksharma/grab_cube. A repo id whose namespace is not you (or a team you belong to) cannot be created — the push fails with a 403.

Path A · Upload the folder you already have

Your first sessions were recorded as me/grab_cube_…. “me” is not your username, so LeRobot's automatic upload could never work for them. The fix is one command — the dataset is just files, so you upload the folder and give it a proper name:

hf upload anjaniksharma/grab_cube \ ~/.cache/huggingface/lerobot/me/grab_cube_20260926_121936 \ --repo-type dataset # then the one thing a plain upload forgets: the version tag (value of codebase_version in meta/info.json) hf repo tag create anjaniksharma/grab_cube v3.0 --repo-type dataset
Don't skip the tag. LeRobot's own push_to_hub() does three things: uploads the folder, writes a dataset card, and creates a git tag named after the format version (v3.0). hf upload only does the first. Without the tag the training pod fails at start-up with “Your dataset must be tagged with a codebase version” — after you've already paid for the pod to boot.

Add --private to the upload if you don't want it public. Uploading the same folder again to the same repo id only sends changed files (re-create the tag afterwards so it points at the new commit: delete it with hf repo tag delete, then create it again). The dataset then lives at huggingface.co/datasets/anjaniksharma/grab_cube, and the Hub's dataset viewer can even play the episodes in the browser.

Path B · Let recording upload for you (next time)

Record with your namespace and leave push_to_hub at its default of true. When you press q at the end of the session the dataset is pushed automatically, with the time stamp in its name:

lerobot-record … --dataset.repo_id=anjaniksharma/grab_cube --dataset.num_episodes=30 # → huggingface.co/datasets/anjaniksharma/grab_cube_20260926_153012
Path C, the lazy one: if you skip both and run lerobot-train … --job.target=… with a dataset that exists only locally under your namespace, LeRobot pushes it for you to a private repo before the job starts. It still can't rescue a me/… name — that's why Path A exists.

Part 7 · Launch

Train on a Hugging Face GPU with one extra flag

lerobot-train normally runs on the machine you type it on. Add --job.target=<gpu> and the same command is packaged up and sent to Hugging Face Jobs: a GPU pod pulls your dataset, trains, and pushes the policy back to the Hub. Pay-as-you-go, per minute.

The command for our cube task

hf jobs hardware # list GPU flavors & prices (a10g-small is the cheap starter) lerobot-train \ --dataset.repo_id=anjaniksharma/grab_cube \ --policy.type=act --policy.device=cuda \ --policy.repo_id=anjaniksharma/act_grab_cube \ --output_dir=outputs/train/act_grab_cube \ --steps=50000 --batch_size=8 --save_freq=10000 \ --wandb.enable=true --wandb.project=so101 \ --job.target=a10g-small --job.timeout=6h

Everything above --job.* is ordinary training config (Parts 2–4). Only the last line changes where it runs.

--job. flagdefaultmeaning
targetNoneGPU flavor from hf jobs hardware (a10g-small, a100-large, h200…). Omitted = run locally.
imagehuggingface/lerobot-gpu:latestthe container the pod boots — LeRobot + CUDA pre-installed
timeout2dwall-clock cap; the job is killed after this, so size it to your step count
detachfalsesubmit and return immediately instead of streaming logs
tags[]extra labels on the job and any repo it creates (lerobot is always added)

What happens when you press Enter

  1. Login check. No token → “Not logged in to Hugging Face. Run hf auth login first.”
  2. Model repo is created up front at anjaniksharma/act_grab_cube (private) holding the training config the pod will run from.
  3. Dataset check. Must be reachable by repo_id; a local-only one under your namespace is pushed private first (Part 6).
  4. Secrets are forwarded: your HF token, and your W&B key if --wandb.enable=true (Part 8). Missing key → the submit refuses.
  5. Submit. You get a job id plus four lines: Job page, Model repo, Monitor, Cancel.
  6. Logs stream into your terminal — the same loss lines you would see locally.
  7. Done: the trained policy (and checkpoints, if --save_checkpoint_to_hub=true) sit in the model repo, ready for lerobot-rollout (Part 9).
Ctrl+C here does the opposite of Chapter 7. It only detaches your terminal — the job keeps training in the cloud. Re-attach with hf jobs logs <id>, list with hf jobs ps, and stop it for real with hf jobs cancel <id> (you pay until you do).

Part 8 · Observability

Watch the loss live with Weights & Biases

The pod is a computer you cannot see. Observability means it reports on itself while it works — so you can tell from your phone whether six hours of GPU time are going well or should be cancelled after ten minutes.

How the numbers get out

Every log_freq steps (default 200) the trainer averages its metrics over that window and, when --wandb.enable=true, sends them to Weights & Biases — a hosted dashboard that plots them the moment they arrive. Each training run becomes a run inside a project; its whole config is attached, so you can compare runs later.

Connect it (once)

wandb login # paste the API key from wandb.ai/authorize → saved in ~/.netrc

That is all the wiring. When you submit a job, LeRobot reads the key from ~/.netrc (or $WANDB_API_KEY) and forwards it to the pod as a secret. If it can't find one it stops before spending money: “wandb is enabled but no WANDB_API_KEY found.”

--wandb. flagdefaultmeaning
enablefalseturn logging on
projectlerobotthe dashboard folder your runs land in, e.g. so101
entityNoneyour W&B username or team; None = your default
notesNonefree text shown on the run (“30 eps, cube moved every time”)
modeonlineoffline logs to disk only, disabled turns it off
disable_artifactfalsetrue = don't also upload each checkpoint to W&B

At start-up the log prints your link: Track this run --> https://wandb.ai/<entity>/so101/runs/<id>. Open it and leave it open.

Points arrive every 200 steps, like the real thing. The eval/eval_loss line appears only in the overfitting scenario because that's the run where episodes were held out — without a held-out split, overfitting is invisible on the dashboard and only shows up on the table (Part 10).

The three loss panels, decoded

Type loss into the dashboard's search box and three panels appear: train/loss, train/l1_loss and train/kld_loss. They are not three different problems — they are one formula, split open.

train/loss = train/l1_loss + 10 × train/kld_lossACT's objective; the 10 is --policy.kl_weight (default 10.0)
panelhealthy shapewhat it measures
train/l1_loss↓ then flatThe one that matters for the arm. Average absolute error, in normalized joint units, between the 100 actions ACT predicted and the 100 you actually performed with the leader. Smaller = its motions are closer to yours. Well-trained SO-101 tasks settle around 0.05–0.15.
train/kld_lossdrops fast, levels off, never 0A regularizer on ACT's hidden “style” vector (a 32-number summary of each demonstration). It measures how far that vector's distribution has drifted from a plain bell curve. Keeping it small means the vector carries little information — so at run time, when it's set to zero because there is no demonstration to summarize, the policy still behaves.
train/lossmirrors l1 once kld flattensJust the weighted sum the optimizer minimizes. Because kld is multiplied by 10 it dominates early, which is why the total starts far higher than l1 ever was.
A real run (11 episodes of grab_cube, step 1 400 of 50 000): l1 0.70 → 0.33, kld 0.60 → 0.14, total 6.7 → 1.7. Check: 0.33 + 10 × 0.14 ≈ 1.7 ✓. Nothing to change — let it run. Red flags would be: l1 plateauing above ~0.3 (inconsistent or too little data), spikes or climbing in either curve (instability), or a suspiciously tiny l1 on a handful of episodes (memorizing — only the rollout on the arm can tell).

Part 9 · Exam Day

🤖 Run the policy on the arm

Training done, policy in hand — now the robot performs alone. Deployment runs a tight loop: look → predict a chunk → move → look again. The command for this is lerobot-rollout (record was for data only).

Press Run and watch the trained policy attempt the grasp on its own.

The autonomous loop

📷 observe→🧠 ACT→🎯 action chunk→⚙️ motors🔁

It executes a few actions from the chunk, looks again, predicts the next chunk, and repeats — the same autoregression that writes text (Chapter 6), but for motion.

lerobot-rollout --policy.path=$HF_USER/act_grab_cube \ --robot.type=so101_follower --robot.port=/dev/tty.usbmodemXXXX --robot.id=my_follower_arm \ --robot.cameras="{front: {type: opencv, index_or_path: 1, width: 640, height: 480, fps: 30}, wrist: {type: opencv, index_or_path: 0, width: 640, height: 480, fps: 30}}" \ --task="Grab the cube" --duration=60
Flip the mismatch switch: if the camera or lighting at deploy time differs from training, the policy misses — the exact lesson from Chapter 7. Your data setup is your deploy setup.
Part 10 · When It Misbehaves

Reading the failures

A misbehaving policy is usually a data or training problem, not bad luck. The fix almost always points back to earlier chapters:

SymptomLikely causeFix
🤪 Jittery, shaky motionJerky demos, or undertrainedSmoother demos (Ch7); train longer
🎯 Reaches the wrong spotCamera moved since trainingPut the camera back exactly (Ch7)
😴 Barely moves / gives upToo few episodes; undertrainedRecord more; more steps
🏠 Works on the bench, fails elsewhereOverfit — no variety in dataVary object position & lighting (Ch7)
💥 Loss never droppedLearning rate too high; bad labelsLower LR; check the task/data
See the pattern? Every deploy failure traces back to data quality or how long/how well you trained. Great robots are built by great teachers with patience. 🧑‍🏫
